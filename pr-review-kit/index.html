PR Review Kit is a Claude Code plugin that reviews Azure DevOps pull requests against a written review policy. It finds the PRs that need attention, reads each one's real diff with cross-repository context, runs merge-conflict, security-scanner and test-compile checks, checks the Jira ticket, then posts a comment and a strict vote.

The reviews are written by Claude. Every write to Azure DevOps goes through one guarded script, and a new install posts nothing until the team owner switches it on. A separate module merges approved PRs, carries them to later branches and deploys them, but only when a person asks.

    How the kit gets there
    
        
      
          
    1. Evidence or nothingEvery point cites the live code at the reviewed commit. A point that cannot be proven from the code is dropped (P1).
      2. 
          
    2. Judged on the PR's own changeMerge base to source tip, so target-branch commits the author merged in are not blamed on the PR. A pre-existing defect is at most an out-of-scope note.
      3. 
          
    3. One thread per teamThe first review opens a thread; every re-review replies in it. The team's comments are recognised by author id and the hidden marker (P11).
      4. 
          
    4. "Fixed" is checked, not trustedAn author's reply is verified against the code. A thread marked fixed with nothing fixed is reopened.
      5. 
          
    5. No security section without a findingThe OWASP grid is applied per change type; scanner output is a candidate, confirmed by hand (P4).
      6.

    The rules are written down, and versioned.
    
      
    A team tunes the settings named under a rule in its config.env; it never edits the rule. Changing a rule means a new kit version, and a change to a vote rule is a major version, announced two weeks ahead and run in dry-run first.

    policy/review-checklist.md§5 Tools
    
    
    
      
    Four checks. A missing tool is reported, never passed.
    
      
    Each optional tool enables one check. When it is missing, that check is skipped and the review says so. Every signal is a candidate to verify against the diff, never a vote by itself, and a failing script is noted briefly while the review continues with the manual grid.
    
    
    
    
    
      
    
        
    check-merge.sh
    
        
    Live conflict with the target, predicted conflicts with sibling PRs via a real git merge-tree trial merge, and semantic collision candidates.
    
        
      
          
    • majorconflict with the target: list files, ask for a rebase
      • 
          
    • minortextual conflict with a sibling PR, plus merge order
      • 
          
    • majorsemantic risk only if confirmed by reading both diffs
      • 
        
    
        
    Needsgit ≥ 2.38 (required by the kit). Every non-Draft PR.
    
      
    
      
    
        
    scan-pr.sh
    
        
    Semgrep on the PR's changed files; Trivy only when dependencies or IaC changed, with CVEs diffed against the base. Kept only if real and introduced by this PR.

      • 
          
    • nonefalse positives are dropped silently
      • 
        
    
        
    If missingsemgrep or trivy not found: skipped, and the review says so.
    
      
    
      
    
        
    check-test-compile.sh

    • env-unverifiablebrief note, not blocking

    /pr-review-kit:review-loopscan.sh → filter.sh → review-pr → ticket votes
    
    
    
      
    The loop only wakes up for a reason.
    
      
    One pass scans the active PRs of the allow-listed repositories, keeps the ones that need attention, handles cheap cases without a full review, reviews the rest grouped by ticket, then re-balances ticket-linked votes. Nothing to do is reported as « board up to date » in one line.
    
    
    
    
    

    
    
      
    
        
    A feature is approved as a whole (P5). Try it.
    
        ticket PROJ-123 · 3 active PRs
      
    
      
    Set the vote each PR merits on its own. While one non-Draft PR of the ticket is at −5, every other non-Draft PR is held at −5 too, with a link to the blocking PR. Draft siblings get comments only.
    
      
    
    
    
  
    

    



    
  
    
    
    /pr-review-kit:merge-deployruns only when a person types it
    
    
    
      
    Approved, then merged, carried over and deployed.
    
      
    The merge module takes the +10 PRs ticket by ticket, merges them in order, carries release fixes to every later release branch and the default branch, moves the Jira tickets, deploys the changed services to a test environment and writes a batch report. It uses a separate token, AZURE_DEVOPS_MERGE_PAT, when set.
    
    
    
    
      
      
    1. FindNon-Draft PRs at +10, grouped by ticket with every active sibling. One sibling at −5 or unreviewed sets the ticket aside.
      2. 
      
    2. Plan and confirmPer ticket: PRs in merge order, the carry-over chain, the services to deploy. Interactive mode waits for a go.
      3. 
      
    3. Merge in orderMigrations → libraries → back-end → front-end, waiting for each merge. Live re-check: vote still +10, no push since the review.
      4. 
      
    4. Resolve conflictsTarget merged into the PR branch, no history rewrite. Import-only hunks resolved by resolve-imports.py; logic conflicts wait for approval.
      5. 
      
    5. Carry overOne cherry-picked commit to each later release branch in semver order, then the default branch. An open twin PR counts.
      6. 
      
    6. Verify presencepresence.sh on every target. ABSENT is investigated before it is reported.
      7. 
      
    7. Move ticketsPer jira-workflow.json, only from the listed statuses; sub-tasks created after checking existing ones.
      8. 
      
    8. Deploy and reportdeploy.sh --dry-run, then -y --wait, followed to the end. Then the batch report and the « To arbitrate » list.
      9. 
    
    
    
    
      
    
        
    A carry-over chain
    
        
    A fix merged on release/1.4, with three later branches. cherry-pick-pr.sh answers one of three results.

    Guard rails
    
        
      
          
    • Never production: environments in PRODUCTION_ENVS are refused.
      • 
          
    • Never a Draft, never −10.
      • 
          
    • Never force-push an author's branch or rewrite history of a branch the kit did not create.
      • 
          
    • Never move a ticket backwards.
      • 
          
    • Never guess: interactive mode asks; autonomous mode sets the ticket aside under « To arbitrate ».
      • 
          
    • Migration PRs need SQL_APPLIED=yes or an explicit go.

    README.mdRequirements · Install · Roll-out
    
    
    
      
    Install, check, then dry-run for a week.
    
      
    The plugin installs from a git marketplace into Claude Code. /pr-review-kit:doctor checks everything at once afterwards.
    
    
    
    
    
      
    
        
    Access on request. The repository is private. Claude Code clones the marketplace with your existing git credentials, so read access has to be granted first.
    

    # 1. in Claude Code: register the marketplace and install the plugin
/plugin marketplace add <repository-url>
/plugin install pr-review-kit@pr-review-tools

# 2. export the secrets in your shell profile, not in any file
export AZURE_DEVOPS_PAT=…   # + JIRA_PAT, GCHAT_WEBHOOK_URL, AZURE_DEVOPS_MERGE_PAT as needed

# 3. create the team workspace, then check everything
/pr-review-kit:setup ~/pr-review/myteam
/pr-review-kit:doctor

# 4. first review, in dry-run: the payload lands in state/outbox/
/pr-review-kit:review-pr <repo> <prId>
