FileFlow 1.0  /  self-hosted file sharing

File sharing where every link answers to its owner.

FileFlow is a file manager for a team's own server. Hand files out by public link, to a colleague, through a team folder, or ask outsiders to drop files in. Each of those grants is checked against its creator's rights on every request, follows the file when it moves, and dies with it.

    drawer 01  /sharing

    Four ways to hand a file over.

    Each one is its own record with its own rules, listed in the sidebar under Sharing, and each one is bounded by what its creator may do in their own right.

    GET /api/s/:token

    Public link

    For anyone outside the server. No account needed.

    • Expiry from 1 hour to 1 year; the server clamps any request to 60 s to 365 days.
    • Password optional, stored as a bcrypt hash; the app can generate one and shows it once.
    • Download limit optional; a limit of 1 makes a one-time link.
    • Range requests for media players, except on capped links.
    POST /api/internal-shares

    Share with a user

    A direct grant from one account to another.

    • Read only or read and write, on a file or a whole folder.
    • Appears in the recipient's Shared with me view.
    • You can only share what you hold in your own right, so access is never re-shared down a chain.
    POST /api/shared-folders

    Team folder

    A named workspace over one folder, with members.

    • Each member gets read or read and write.
    • Members can never get more than the creator holds, and that is re-checked on every access.
    • If the creator loses access, the members lose it too.
    POST /api/r/:token

    Upload request

    A drop box: outsiders send files into one folder.

    • Optional password and expiry.
    • Needs write access from its creator, re-checked on every upload.
    • Never overwrites anything: a clash becomes report (1).txt.
    • Size capped by PUBLIC_UPLOAD_MAX_MB; executable types refused.
    drawer 02  /security

    The rules every request is filed under.

    Nine clauses taken from the code. Most of them exist because a review asked how a shared file could escape its owner, and the answer had to be enforced in one place.

    § 1  CANONICAL PATHS

    The path that is checked is the path that is opened

    Every client path goes through normalize_virtual: .. is rejected outright, . and empty segments dropped. Prefix checks respect segment boundaries, so /proj never covers /projects. Symlinks are resolved and must stay inside the root.

    § 2  DERIVED AUTHORITY

    No grant outlives or outranks its creator

    Public links, upload requests and team folders are re-checked against the creator's own rights on each request. A disabled account or a revoked group turns its links into the same anonymous 404.

    § 3  LIFECYCLE

    Links follow the file

    Rename or move a file and its links, upload requests, shares, team folders, favourites and tags move with it. Delete it and they are purged, so a link can never attach to whatever is created at that path next.

    § 4  DOWNLOAD CAPS

    One-time means one time

    Checking the cap and counting the download is a single atomic step (try_reserve_download), refunded if the transfer fails. Capped links ignore Range, so a file can't be pulled in pieces. A test fires 50 parallel reservations at a one-time link and expects exactly one.

    § 5  LOGIN LOCKOUT

    Three counters, so nobody can lock you out cheaply

    5 failures per IP, 5 per username and IP, and 50 per account across all IPs, each locking for 15 minutes. Unknown usernames still pay a bcrypt hash, so timing does not reveal which accounts exist.

    § 6  LINK PASSWORDS

    Guessing a link password is throttled

    Failures count against the link and against the client IP, 5 each, checked before any bcrypt work. A correct password clears only the link counter, so a known link can't be used to reset an IP.

    § 7  REVOCABLE SESSIONS

    Every session can be ended

    Sessions are HS256 tokens in an HttpOnly, SameSite=Strict cookie. Each carries a tv claim that must match the account's token_version; changing a password, "log out everywhere" or an admin revoke bumps it. It starts at a random value, so a re-created account can't reuse old tokens.

    § 8  TWO FACTORS

    2FA, with step-up to change it

    TOTP enrolment by QR code, plus 10 one-time recovery codes stored as bcrypt hashes. Disabling 2FA or regenerating codes needs the password and a current code. Turning 2FA on or off ends every other session. The 2FA step has its own lockout.

    § 9  BROWSER

    Uploaded files never run in the app

    A strict CSP (script-src 'self'), nosniff, no-referrer, COOP, a deny-all Permissions-Policy, and HSTS behind TLS. HTML, SVG and XML previews are served as plain text. 21 executable extensions are refused at upload.

        drawer 05  /architecture

        One process, two folders, nothing else to run.

        The binary serves the built React app and the JSON API on one port. Files stay plain files on disk; everything about them lives in a single SQLite file next to an append-only audit log.

        Scroll the diagram sideways.

        No broker, no cache server

        Rate limiters, upload sessions and the read cache live in the process. A background task tidies them every 30 minutes and purges expired links. Shutdown on SIGTERM lets in-flight requests finish.

        SQLite as a document store

        Each record is one row holding its JSON, so a change is a single-row write instead of rewriting a whole file. Older JSON stores are imported on first start and left untouched.

        Files stay files

        Your data is a normal directory tree you can back up with anything. Versions, trash and tags sit in a hidden .fileflow folder that no request path can reach.

        Lint rules with teeth

        Clippy treats unwrap_used, dbg! and todo! as errors in CI. A panic in a request path is a remotely triggerable crash, so the code handles the error or states the invariant with expect().

        Fuzzing where input is hostile

        The four fuzz targets cover HTTP Range parsing, uploaded file names, download headers and path resolution: the places where a stranger's bytes meet the file system.

        Pure-Rust crypto

        JWT signing uses the pure-Rust HS256 backend, and SQLite is compiled in. No OpenSSL and no C runtime, which is what lets the binary run on a distroless static image.

        drawer 07  /install

        Build one image, mount two folders.

        A three-stage Dockerfile builds the app with Node, the server as a fully static musl binary, and copies both onto distroless/static running as UID 65532. The image has no shell; its health check is the binary itself.

        The source is private. FileFlow is not published as a public image or repository. Access to the code and the Dockerfile is available on request from the author.
